# v1.0 core vs v0.13.1 (measured 2026-10-15)

The HttpArena entry (`benches/httparena`) at each version, built from its Dockerfile, same dataset, same host,
same session. v0.13.1 is the `epoll_cores` (tuned) entry; v1 is the standard-mode entry on the 1.0 core.

**Host:** Ryzen 5 3600 (6 cores / 12 threads, bare metal), Linux 6.8, Docker. The host runs other services
(idle during the run, load average ~0.5).
**Pinning:** server on 4 physical cores (`--cpuset-cpus 0-3,6-9`, 8 threads), wrk on the other 2 cores
(`4,5,10,11`). wrk joins the server container's network namespace (loopback, no published port, no proxy).
**Load:** wrk `-t4 -c256`, 3 s warmup, three 10 s runs, median shown.

| Profile | v0.13.1 | v1.0.0 | v1 + pin fix | v1 + fix vs v0.13.1 |
|---------|--------:|-------:|-------------:|-------------------:|
| baseline `GET /baseline11?a=1&b=2` | 313.7k | 310.0k | 309.2k | 0.99× (client-bound) |
| pipelined `GET /pipeline`, depth 16 | 1.30M | 2.72M | 2.71M | **2.09×** |
| json-comp `GET /json/40?m=3`, gzip | 21.7k | 19.9k | 51.6k | **2.38×** |

Server memory under load (docker stats): v0.13.1 14 MiB, v1 54 MiB. v1 keeps per-connection read/write
buffers and a per-worker compressor for the connection's life; not investigated further.

## Reading the rows

- **baseline** is wrk-bound here (two client cores). Server CPU per request tells them apart: v1 13.0 µs,
  v0.13.1 16.5 µs (`docker stats` CPU% over req/s, 8 s runs).
- **pipelined** is where one `send` per batch and no per-request allocation show: 2.1× at the same CPU budget.
- **json-comp** regressed in 1.0.0 and the fix below brings it to 2.4× v0.13.1.

## The json-comp regression in 1.0.0

Both versions produce byte-identical responses (6688 B JSON, 1268 B gzip) with the same miniz level, yet
1.0.0 spent 400 µs of CPU per request on 8 threads against 161 µs (raw JSON) for v0.13.1. Single-threaded, the
1.0 encoder took 48 µs for the page, faster than vlib's `json.encode` (74 µs), and allocated nothing. With more
threads it did not scale at all (50 → 85 → 182 → 335 µs per round at 1/2/4/8 threads).

`perf` in the container: 20% in `GC_lock`, 6% in `GC_remove_roots`. The cause is V 0.5.2's `-prod` code
generation for Boehm. Around every call statement it walks each by-value struct, or array of pointers, in
scope, and past 32 pointers it `calloc`s a root list and registers it under the global GC lock
(`GC_add_roots`/`GC_remove_roots`). The array encoder made a call per item with the whole page in scope:
40 walks of ~240 pointers and 40 global locks per request. The engine's event loop had the same shape: a
by-value `Loop` holding the conns array around every `on_event` call. With more than 32 conns per worker,
as on HttpArena's 4096-connection profiles, every event took the lock. The zero-allocation gate could not
see any of this, because nothing lands on the GC heap.

Fix (commit `perf(jsonenc,engine)`): calls made while a struct or array is in scope are written as
`_ = f()` (assignments are not pinned), `Loop` lives on the heap, and `scripts/gcpin_check.sh` fails CI on a
pin in any hot-path function. Handler code in apps can hit the same thing; see
[docs/request-response.md](../../docs/request-response.md#handlers-and--prod).

## Reproduce

The scripts used live outside the repo. The setup: build each `benches/httparena/Dockerfile` (v0.13.1 with
`--build-arg VILTRUM_REF=v0.13.1`), run it with `-v <dir with dataset.json>:/data:ro --cpuset-cpus 0-3,6-9`,
and drive it with
`docker run --rm --network container:<server> --cpuset-cpus 4,5,10,11 <alpine+wrk> wrk -t4 -c256 -d10s …`
(pipelined: the usual 16-request `pipeline.lua`; json-comp: `-H 'Accept-Encoding: gzip'`).
